### CourtListener Pipeline — `scripts/scrape/scrape_courtlistener.py` + `scripts/ingest/ingest_courtlistener.py`

**Exploration:** Wrote and ran `scripts/scrape/explore_courtlistener.py` to characterize the CourtListener API v4. Key findings:
- Auth token works; uses `Token` header
- `/search/?type=o` endpoint is fast (0.6s); `/clusters/` endpoint times out (>60s) — use search
- `plain_text` often empty; `html_with_citations` has full text — strip HTML tags
- Opinions filterable by cluster ID via `/opinions/?cluster=<id>` (fast, avoids extra cluster fetch)
- No explicit rate-limit headers; 429s enforced silently; 502s are transient and retry-safe
- `count` field quirk: returns URL string when `fields=` param is passed — don't use for counts
- ~57,977 total immigration-related opinions across 13 circuits from 2000-present

**Scraper design decisions:**
- Pagination: `/search/` endpoint with cursor (not `/clusters/` — too slow)
- Text fetch: `/opinions/?cluster=<id>` directly (2 API calls per opinion, no extra cluster hop)
- Text field priority: `plain_text` → `html_with_citations` → `xml_harvard` → `html`
- Rate limiting: 0.5s sleep between requests, 65s backoff on 429, retry on 502/timeout
- Storage: one JSON file per cluster at `~/courtlistener_opinions/<court_id>/<cluster_id>.json`
- Idempotent: skips files already on disk

**Ingest design:**
- Corpus: `court_opinions`
- source_id: cluster_id (TEXT)
- source_label: "Case Name (Citation) [COURT]"
- source_date: date_filed
- Standard 800-token / 80-token overlap paragraph chunking
- `ensure_corpus_allowed()` uses `NOT VALID` constraint to avoid scanning existing rows
- `--ingest` / `--embed` / `--status` / `--reset` / `--court` / `--limit` flags

**Status:** Scrape running as of 2026-05-01, currently mid-ca2 after completing scotus (~13,500 opinions). All 13 circuits queued from 2000-present. Ingest + embed deferred until scrape completes. Note: broad court+date filter (not keyword filter) — will capture all published opinions, not just immigration-specific. Consider adding keyword filter at ingest time to reduce non-immigration noise.

## OEWS Wage Prediction Model — Data Collection Phase

### Research: OFLC wage calculation methodology
- OFLC does NOT publish OEWS percentile values directly. BLS provides custom tabulations:
  - Level I = mean of lowest-paid 1/3 of workers (~17th pctile)
  - Level IV = mean of highest-paid 2/3 of workers (~67th pctile)
  - Level II = L1 + (1/3)(L4 - L1)
  - Level III = L1 + (2/3)(L4 - L1)
- BLS uses rolling 6-panel MB3 model (3 years of semiannual surveys)
  - May 2025 OEWS uses panels: May25, Nov24, May24, Nov23, May23, Nov22
  - Older panels are aged forward to May reference date using ECI as the aging factor
  - ECI series used: private industry wages & salaries by occupational group
- Published BLS percentile figures (10/25/50/75/90) are NOT identical to OFLC's L1-L4
- May 2025 BLS OEWS release: May 15, 2026 — this IS the source for July 2026 OFLC update
- NPRM (ETA-2026-0001, 91 FR 15454, Mar 27 2026): would raise pctiles to 34/52/70/88
  - Comment period closed May 26, 2026. Not yet finalized. July 1 update uses current method.

=== 2026-06-18 Session (continued) — PWD City/State Parsing Fix ===

## Bug fixed

**Problem**: When a PWD PDF was dropped onto the PERM Comparer, the city field was
receiving the entire "City State Zip" string (e.g., "Richardson TX 75080") instead
of splitting into city and state correctly.

**Root cause**: pdfplumber frequently collapses city/state/zip columns into a
single-space-separated string when extracting text from the ETA-9141 form.
The Layout A parser split on 2+ spaces, so if the PDF had only single spaces
between city/state/zip, the entire string landed in parts[0] (city) with
parts[1] (state) empty.

**Fix**: Added `_US_STATES` set and `_split_city_state_zip(raw_city, raw_state)`
helper to `app/extract_pwd.py`. The helper handles all four failure modes:
  - `"Richardson TX 75080", ""` → strips zip, splits state from city tail
  - `"Richardson TX", ""`       → splits state from city tail
  - `"Richardson", "TX 75080"`  → strips zip from state field
  - `"New York", "NY"`          → already correct, no change

Helper is called at every city/state extraction point in both `_extract_new`
(Layout A + Layout B) and `_extract_old` (Layout A + Layout B).

### Why generic ingest failed
These files use a WIDE PIVOT format: each column is a priority date year
(10-year sliding window), not a metric. The generic ingest_uscis_stats.py
header detector couldn't map "Priority Date Year - 2013" to any canonical
field, so all 25 files yielded 0 rows.

### Layout (consistent across all 25 files)
  Row 0: "Form I-485, Application to Register Permanent Residence..."
  Row 1: Report title with country and year range
  Row 2: "As of <Month> <Day>, <Year>"  <- report_date extracted here
  Row 3: Column headers (15 columns, always same structure)
  Row 4+: Data rows
  Col 0: Country Of Chargeability
  Col 1: Preference Category (full text -> normalized to EB1/EB2/etc.)
  Col 2: Visa Status (Available / Awaiting Availability)
  Col 3: Priority Date Month
  Col 4-14: Priority Date Year - YYYY (or "Prior Years")
  "D" = suppressed (<10 cases) -> stored as NULL with is_suppressed=TRUE
  "0" = genuinely zero

  - Mexico EB2/EB3: similar reason — spread rarely creates downgrade pressure

The eb2_ahead regime is actionable across ALL countries. When EB2 is ahead
of EB3 for any country, clearance predictions are accurate within ~2.4 months.
